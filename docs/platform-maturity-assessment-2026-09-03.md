# AutoTest AI 平台成熟度评估

评估日期：2026-09-03

## 一、总体结论

当前项目已经超过“生成几个脚本的 AI Demo”，具备需求包隔离、测试设计、账号建模、工具编排、数据证据、报告回收和复盘的完整产品骨架。

成熟度定位：**M3 - 已集成、可演示、可继续试用的质量中枢 MVP**。

还没有达到 M4 团队稳定试用或 M5 企业生产级，主要原因不是功能少，而是：

- 工资交易复杂链路尚未取得一次全部关键状态流通过的真实验收结果。
- Apifox OpenAPI 链路已真实落盘，但 Apifox CLI 仍未用企业真实套件完成首轮运行。
- 后端和前端仍有明显单文件集中问题，自动化测试覆盖面小于功能面。
- 缺少 CI、远程仓库、任务队列、权限体系和企业级凭证管理。

综合评分：**68/100**。

## 三、完整协作链路

```text
需求文档 / 抓包 / Apifox OpenAPI
        ↓
需求包识别与隔离
        ↓
测试点、结构化测试用例、异常与边界场景
        ↓
账号模型 + 资源清单 + 数据准备预检
        ↓
场景执行计划 execution-plan.json
        ↓
Apifox CLI / Newman / JMeter / pytest / 人工复核
        ↓
HTTP结果 + JTL/HTML + DB/Redis只读证据
        ↓
run-context统一运行批次
        ↓
统一场景报告 + AI复盘 + 人工维护入口
```

平台的核心价值不是替代所有工具，而是保证同一个需求在不同工具之间仍然保持同一套场景、账号、变量、证据和报告上下文。

## 四、功能实现、协作方式与日常价值

### 1. 需求与接口资料接入

实现方式：

- 支持需求文字、HTML、文件、OpenAPI/Swagger、HAR和网页资料。
- FastAPI接收资料，旧核心层负责解析和写入SQLite。
- 接口导入支持版本批次、接口变更和需求关联。

协作方式：资料是测试点、用例、接口资产、场景计划和报告追踪的共同上游。

优势：不要求测试人员先把长需求手工整理成表格，再开始设计测试。

解决的问题：需求文档太长、接口散落、真实请求和文档不一致、测试依据难追踪。

成熟度：**75%**。解析能力丰富，但输入质量差时仍需要人工确认，接口真相源治理还在向Apifox收口。

### 2. 需求包隔离

实现方式：

- 每个需求使用独立 `requirements/<package_id>`。
- 包内维护 `manifest.json`、账号模型、资源清单、证据规则、脚本、运行批次和报告。
- 报告按 `package_id + run_id` 过滤，不再混用旧全局报告。

协作方式：所有工具先选择需求包，再读取该包的配置和资产。

优势：财富等级、工资交易和未来需求不会再覆盖同一份JMX、CSV或报告。

解决的问题：不同需求变量混乱、旧脚本被覆盖、报告堆在一起无法定位。

成熟度：**85%**。这是当前项目最稳定、最有产品价值的基础能力之一。

### 3. 结构化测试用例

实现方式：

- `generate_structured_test_cases` 汇总数据库用例、正式证据规则和候选证据规则。
- 输出JSON、Markdown和Excel。
- 用例包含前置条件、步骤、预期结果、异常来源、质量等级和自动化准备状态。

协作方式：结构化用例向下驱动账号模型、工具分流、JMeter映射和pytest证据。

优势：不仅生成“标题+预期”，还能告诉测试人员是否缺数据、缺证据、只能手工验证或已经可脚本化。

解决的问题：长需求看不完、测试步骤难落地、正常和异常场景遗漏、测试用例与自动化脱节。

成熟度：**80%**。输出完整，但用例数量较大，仍需要去重、风险分层和重点主链路视图。

### 4. 多账号与角色模型

实现方式：

- `account-model-generation` Skill判断单账号、双角色、多流程槽位或数据矩阵。
- 每个需求生成独立 `account_model.yaml`。
- 身份来源按运行参数、CSV、登录接口、Redis缓存顺序解析。
- JWT可解析时校验token中的uid与角色uid一致。

协作方式：Newman、JMeter、pytest共享账号模型，不再分别猜申请人、代理人或普通用户。

优势：账号复杂度由测试用例和业务约束决定，不默认强制每个需求使用CSV或Redis。

解决的问题：单账号需求被双角色配置阻断、8条流程重复使用同一申请人、代理ticket与uid不匹配导致401。

成熟度：**72%**。规则设计成熟，但工资交易真实多账号执行尚未完整通过。

### 5. 资源清单与运行前预检

实现方式：

- `resource_manifest.yaml` 声明当前需求需要的账号、CSV、DB表、Redis Key和运行变量。
- `requirement_resource_preflight` 检查资源是否存在。
- 数据预检按场景检查账号槽位、币种、代理匹配、凭证和业务前置数据。

协作方式：执行器启动前先消费预检结论，阻断时给出缺失资源和下一步动作。

优势：尽量把401、50017、代理匹配失败和订单号缺失提前暴露。

解决的问题：脚本跑到中间才发现账号无效、申请人已有处理中订单、代理不支持目标币种。

成熟度：**70%**。静态预检可用，实时登录态和业务数据可用性检查还不够稳定。

### 6. 测试用例到JMeter映射

实现方式：

- 输出 `case-jmeter-mapping.json`。
- 记录用例ID、线程组、采样器、变量、断言和DB/Redis证据规则。
- JMeter Skill定义线程组、CSV、断言、监听器、压测场景和报告契约。

协作方式：测试用例决定测什么，账号模型决定用谁测，映射表连接用例和实际JMX组件。

优势：可以回答“这个用例是否被JMeter覆盖”，不需要打开JMeter逐层查找。

解决的问题：测试用例和JMX长期脱节，脚本维护者不知道修改影响哪些业务场景。

成熟度：**78%**。映射资产较完整，但生成器仍包含工资交易专用逻辑，需要继续通用化。

### 7. 工具分流与场景执行计划

实现方式：

- `test-tool-routing` Skill按业务场景生成 `execution-plan.json`。
- 不按HTTP方法简单分流，而是判断状态依赖、角色切换、证据深度、并发和人工等待。

协作方式：一个场景下面挂Newman、JMeter、pytest和人工动作，而不是把一个需求拆成几个互不相关的项目。

优势：保留企业工具分工，同时保持人工维护仍以业务场景为中心。

解决的问题：Newman/JMeter/pytest报告分散，测试人员不知道同一流程在哪个工具里维护。

成熟度：**82%**。设计正确，是平台区别于普通脚本生成器的重要能力。

### 8. Newman接口回归

实现方式：

- 按需求包生成Postman Collection。
- Newman执行后回收JSON结果。
- 二次生成逐接口失败分类、响应摘要、建议负责人和复核动作。

协作方式：负责轻量接口回归、鉴权冒烟和简单契约检查；结果进入run-context和统一报告。

优势：失败不只显示“请求失败”，还能区分鉴权、参数、环境、服务端和业务断言问题。

解决的问题：发布前人工逐接口点请求、失败后无法快速分派责任人。

成熟度：**78%**。财富等级已真实通过；工资交易能发现问题，但登录态仍导致大量401。

### 9. JMeter流程与性能

实现方式：

- 生成JMX、运行参数、启动脚本和映射manifest。
- 支持复杂状态流、多账号CSV、变量提取、JDBC只读查询、断言和监听器。
- 可回收JTL、原生HTML、P95/P99、吞吐量、错误率和慢接口。
- 压测采用预案和明确阶梯，不由普通回归静默启动。

协作方式：负责复杂状态机、并发、基准、阶梯和稳定性；pytest和AI复盘读取其结果。

优势：保留企业认可的原生JMeter，人看HTML，平台看结构化指标。

解决的问题：复杂流程仅靠Postman难维护、性能结果只能人工翻JTL、脚本与业务用例无法对应。

成熟度：**67%**。生成和回收能力较强，但工资交易真实状态机和财富等级性能阈值尚未通过。

### 10. pytest深度证据层

实现方式：

- 读取需求包主编排文件、结构化用例、账号模型和 `evidence_rules.yaml`。
- 按场景顺序执行HTTP、提取运行变量，再执行DB/Redis证据。
- 可以读取Newman JSON和JMeter JTL作为复盘输入。
- 输出场景化证据JSON。

协作方式：不替代JMeter状态机，而是负责执行后深度核验和跨层证据汇总。

优势：不只看HTTP 200，还能验证订单、金额、状态、日志和缓存是否符合预期。

解决的问题：接口返回成功但数据库未落库、状态不一致、最后一个orderNo覆盖前面场景变量。

成熟度：**76%**。财富等级已真实通过，工资交易受前置账号和订单变量阻断。

### 11. DB/Redis证据规则

实现方式：

- 正式规则使用 `evidence_rules.yaml`。
- AI可以生成候选规则，但不会自动覆盖正式规则。
- MySQL/Redis执行限制为只读。
- 工资交易限定4张业务表，Redis明确为非必需资源。

协作方式：结构化用例、预检、pytest和AI复盘共同消费同一份证据规则。

优势：数据源按需求声明，不默认认为每个需求都有Redis或固定表结构。

解决的问题：接口测试只看响应、AI编造表字段、数据库被错误当作ticket来源。

成熟度：**78%**。DB方向已经形成亮点，Redis元数据和跨项目通用映射仍需更多样本验证。

### 12. AI幻觉静态校验与一次修正

实现方式：

- `metadata_hallucination_audit` 扫描结构化用例、候选规则、账号模型和映射。
- 与真实DB表、字段、Redis Key或Pattern比较。
- 未证实引用进入修正版目录并降级为人工确认，不覆盖正式资产。

协作方式：位于“AI生成之后、正式执行之前”，为测试资产增加真实性门槛。

优势：比只校验HTTP字段的普通AI测试Demo更接近真实企业数据环境。

解决的问题：AI生成不存在的表名、字段名、Redis Key，测试人员运行后才发现完全不可用。

成熟度：**75%**。静态规则完整，但修正主要是降级和标记，并非真正理解业务后重写全部资产。

### 13. Apifox企业链路

实现方式：

- 从Apifox导入OpenAPI 3.0并归档版本。
- 全量生成当前需求包的pytest基础接口，人工business目录不覆盖。
- Apifox CLI命令按需求包配置，token来自环境变量。
- CLI日志和原生JSON/HTML可回收到当前运行批次并脱敏。

协作方式：Apifox维护接口真相、Mock、人工调试和发布冒烟；平台负责生成、执行回收和复盘。

优势：不要求公司放弃已有Apifox，也不在平台重复造接口文档工具。

解决的问题：接口真相源重复维护、脚本生成缺少可靠Schema、发布冒烟结果无法进入统一报告。

成熟度：**65%**。OpenAPI链路已真实完成，CLI链路代码和测试完成，但还缺企业真实套件验收。

### 14. 运行批次与报告中心

实现方式：

- 每次运行生成 `run-context.json`。
- Newman、JMeter、pytest、数据证据、性能分析、场景报告和AI复盘挂到同一run_id。
- 报告中心先选需求包，再选运行批次和报告分类。
- 有最新报告、历史归档和保留策略。

协作方式：所有执行工具最终回到一个业务批次，不再用文件名猜测报告属于哪个需求。

优势：原始报告、人类可读报告和AI分析同时保留。

解决的问题：报告数量多、不同需求混在一起、最新报告与历史累计JTL混淆。

成熟度：**83%**。当前工资交易41份、财富等级54份报告已按包管理，是平台较成熟的模块。

### 15. AI执行复盘

实现方式：

- 汇总接口状态、Newman失败、JMeter指标、pytest场景证据和DB/Redis结果。
- 按鉴权、测试数据、请求契约、业务断言、环境、服务端和性能分类。
- 输出P0/P1、建议负责人、复核动作和证据来源。
- 性能分析可在配置模型时调用模型，缺少模型时使用内置确定性分析。

协作方式：位于所有工具执行之后，只输出结论和建议，不自动修改正式脚本或业务数据。

优势：既保留可解释规则，又能接入模型增强，不走不可控的自主循环。

解决的问题：测试人员需要同时阅读HTTP响应、JTL、数据库查询和缓存结果才能定位原因。

成熟度：**72%**。分析结构完整，但“规则分析”和“真实模型分析”在界面上还需要明确标识。

### 16. YAML配置、迁移和启动

实现方式：

- `config/env*.yaml` 保存环境、工具、开关、路径和报告策略。
- 敏感值使用环境变量或本机文件。
- `.venv` 隔离Python运行环境。
- `platform.cmd setup/check/start` 负责安装、验证和启动。

协作方式：所有生成器和执行器读取统一环境配置，需求运行数据再由CSV或运行参数提供。

优势：配置和脚本数据边界清楚，换电脑时不依赖Codex自带Python。

解决的问题：本机Python版本混乱、缺uvicorn/PyYAML/Pydantic、JMeter路径写死、迁移后无法启动。

成熟度：**72%**。迁移检查可用，但Windows优先明显，`pyproject.toml`与`requirements.txt`依赖仍未完全一致。

### 17. 工作台UI

实现方式：

- 左侧收敛为质量总览、需求资产、执行中心、数据验证和报告中心。
- 执行中心围绕当前需求包和run_id组织操作。
- 报告中心按需求包、批次和报告类型展示。

协作方式：UI调用FastAPI，FastAPI目前大量委托给旧 `app.py` 核心实现。

优势：已经从“所有功能平铺”转向“需求包主流程”。

解决的问题：入口太多、工资交易写死、找不到脚本、报告混合、重新生成不知道从哪里操作。

成熟度：**60%**。逻辑方向正确，但 `app.js` 仍是大型单文件，部分入口仍有重复和隐藏问题。

## 五、平台最有竞争力的优势

### 1. 不是只生成脚本，而是维护需求上下文

同一需求包同时保存测试用例、账号、脚本、证据和报告。未来接口变化时可以定位受影响场景，而不是重新生成一堆孤立文件。

### 2. 场景优先，而不是工具优先

Newman、JMeter和pytest只是执行方式。人工维护仍然围绕“创建后取消”“代理拒绝”“完整成交”等业务流程。

### 3. 多账号建模是实际业务能力

平台知道单账号、双角色和多流程槽位的区别，也知道DB候选身份与真实登录凭证不是一回事。这比简单CSV参数化更接近复杂业务测试。

### 4. HTTP、DB、Redis证据统一

平台能够回答“接口是否成功”和“业务数据是否真的正确”两个不同问题。

### 5. AI幻觉校验有真实元数据依据

AI输出必须经过真实表、字段和Key验证。这个能力可以作为项目展示和面试中的核心差异点。

### 6. 人看原始报告，AI负责归纳

JMeter HTML、JTL、Newman JSON和pytest证据仍然保留，AI结论不能替代原始证据，减少黑盒感。

### 7. 可以接企业已有工具

Apifox、JMeter、pytest、MySQL和Redis继续保留原本职责，平台做连接和治理，更容易被实际团队接受。

## 六、当前主要风险

### P0：必须优先解决

1. **工资交易尚无完整成功批次**：必须使用有效申请人/代理凭证，至少真实跑通一条完整成交链路，再扩展8场景。
2. **Apifox CLI尚未真实验收**：需要企业套件ID、CLI命令和token跑一次，确认原生报告回收格式。
3. **代码与资产未形成干净基线提交**：大量改动和生成文件未提交，出现回归时难以确定变化来源。

### P1：进入团队试用前解决

1. `app.py` 约1.6万行，FastAPI多数路由仍直接调用legacy函数，服务层迁移只完成雏形。
2. `static/app.js` 超过400KB，需求包、执行、报告和数据预检尚未真正拆模块。
3. 21个测试无法覆盖117个路由、522个核心函数和大量外部工具分支。
4. `quality_hub_backend/adapters/jmeter.py` 的导入路径仍指向不存在的 `app.adapters`，说明新Adapter层没有被真实执行覆盖。
5. `pyproject.toml` 缺少 `PyYAML` 和 `PyMySQL`，与 `requirements.txt` 不一致。
6. 外部工具执行主要是同步请求，没有后台任务队列、取消、进度持久化和断线恢复。
7. Schema审计是自定义基础校验，尚未形成正式JSON Schema/Pydantic版本迁移体系。

### P2：生产化再解决

1. 平台没有登录、RBAC、项目权限和操作审计。
2. 凭证主要依赖环境变量和本机加密文件，尚未接企业Secret/Vault。
3. 没有CI流水线、远程Git仓库、Docker或Linux启动链路。
4. 没有统一日志、指标、链路追踪和执行容量限制。
5. 多模型协作和Agent演进目前只有规则、Skill和接口基础，没有正式调度器。

## 七、日常工作中能解决什么

| 日常问题 | 平台提供的解决方式 |
| --- | --- |
| 需求太长，测试不知道从哪里开始 | 自动生成结构化正常、异常、边界和流程用例 |
| 不同需求脚本和报告混在一起 | 需求包与run_id双层隔离 |
| 一个需求有多角色、多账号 | 自动生成账号模型和流程槽位规则 |
| 经常遇到401才发现ticket不对 | 执行前校验uid、ticket来源和账号槽位 |
| 接口200但数据库状态不对 | pytest结合DB/Redis证据核验 |
| AI编造表名和Redis Key | 元数据幻觉审计和一次修正输出 |
| JMeter脚本与测试用例对不上 | 用例到线程组、采样器、变量和断言映射 |
| 报告太多，不知道先看哪个 | 统一场景报告和AI失败分类 |
| 公司已经使用Apifox | 导入OpenAPI、生成pytest、回收CLI冒烟结果 |
| 换电脑后依赖和路径全部失效 | 项目虚拟环境、YAML配置和迁移检查 |

## 九、适合对外说明的项目定位

> AutoTest AI 是一个面向复杂业务接口测试的质量编排中枢。它从需求和接口资产生成结构化测试用例，按业务场景决定使用Apifox/Newman、JMeter或pytest，自动建立多账号、运行变量和DB/Redis证据关系，并把原始报告回收为统一场景报告和AI复盘。平台不替代企业已有测试工具，而是解决需求、脚本、账号、数据证据和报告之间长期割裂的问题。

当前最准确的表达是：**可运行、可迁移、具有明显业务亮点的完整MVP，尚在从个人项目向团队试用版本过渡。**
