# JMeter MCP adoption

## Decision

The platform keeps its JMeter Skill as the business decision and constrained
JMX generation layer. `jmeter-mcp-server` is the execution and report kernel.

The platform exposes one JMeter engine:

1. Requirement cases, OpenAPI and the selected Profile are compiled by the Skill into `jmeter-plan.jmx`.
2. The deterministic gate validates the JMX and performs at most one format-only correction pass.
3. The MCP workflow contains `source_jmx` and execution thresholds only. The bridge imports the approved plan and runs JMeter in non-GUI mode.
4. JTL, native HTML and MCP aggregate analysis are returned to the existing requirement run context.
5. The platform adds DB/Redis evidence, thresholds and AI review after the run.

## Ownership boundary

- Skill: tool choice, business flow, role/account model, assertions and load profile.
- MCP: approved JMX import, non-GUI execution and JTL/HTML artifact collection only.
- JMeter: the actual load generator and native HTML dashboard.
- Quality Hub: preflight, secrets, report batches, thresholds, evidence and AI review.

## Security boundary

`jmeter-mcp-server@0.3.1` does not accept runtime `-J` properties in
`execute_test_plan`, and its imported CSV binding is not reliable enough for
credentials. The platform therefore reads the approved requirement data source,
builds a thread-bound account pool, serializes it as Base64 JSON and exposes it
only in the child-process environment. The generated JMX selects one row by
JMeter thread number and pins that identity for the thread lifetime. Raw ticket,
token, cookie and authorization values are never written into JMX, workflow,
JTL, HTML, MCP summaries or AI reports.

## Install and verify

```powershell
cd C:\path\to\AutoTest-AI
npm install --prefix .\tools\jmeter-mcp
$env:AUTOTEST_JMETER_HOME = "C:\path\to\apache-jmeter-5.6.3"
powershell -ExecutionPolicy Bypass -File .\scripts\run-jmeter-mcp-poc.ps1
```

The default POC starts a temporary local read-only health endpoint. It writes
JMX, JTL, HTML, JMeter log, aggregate metrics and threshold analysis under
`reports/jmeter-mcp-poc`.

Pass `-UsePlatformHealth` only while the platform is already running on the URL
declared in `examples/jmeter-mcp/health-workflow.json`.

## Acceptance gate

Keep the single MCP gateway only while these checks remain green:

- multi-sampler request chains and extractors
- process-scoped account-pool binding on another machine
- credential placeholder execution without secret persistence
- scenario and performance report ingestion into one requirement run context
- failure classification for HTTP, assertion, timeout and JMeter startup errors
- adapter unit tests and one real integration test in CI

## Performance baseline

Every run context carries a performance baseline state and a comparison state.
An eligible first run is a candidate; it becomes active only after manual
approval. Comparison is allowed only for the same environment, Profile and
target fingerprint. JTL-only diagnosis reports possible bottlenecks as
hypotheses and requests DB, Redis, APM or host evidence before root-cause claims.

Request throughput and business transaction throughput are separate contracts.
A request-only plan reports RPS only. TPS is published only when the selected
execution-plan scenario has an explicit scenario id, at least two ordered ready
steps, no blockers, and a Transaction Controller generated by the performance
Skill. Legacy transaction parent samples are ignored when that contract is not
present.
